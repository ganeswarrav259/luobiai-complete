# AI 协作快速上手：用 Codex × 飞书 CLI 完成项目工作

适用对象：落笔 AI 项目的所有协作者。你不需要先学会命令行；把目标、链接和验收标准说清楚，让 Codex 代为读取、整理、编写和提交。每个影响项目的改动仍要遵循飞书看板与 GitHub PR 流程。

> **安全底线：** 每个人用自己的飞书和 GitHub 账号授权；不要把 App Secret、访问令牌、二维码、密码或任何密钥发到群聊、飞书文档或提示词中。拿不准是否会改动内容时，先要求 Codex「只读取并给方案」。

## 1. 两个工具分别做什么

| 工具 | 最适合做什么 | 你需要提供什么 |
| --- | --- | --- |
| Codex | 理解需求、读代码、写改动、解释报错、生成 PR、整理文档 | 目标、相关链接、范围、验收标准 |
| 飞书 CLI | 让 Codex 读取或更新你有权限访问的飞书文件夹、文档和多维表格 | 你自己的授权，以及对应的飞书链接 |
| GitHub | 保存代码、分支开发、PR 审阅和合并历史 | 仓库权限、分支和 PR 链接 |

## 2. 首次使用（每位成员各做一次）

1. 确认自己已加入飞书项目文件夹，并能打开问题看板。
2. 在自己的 Codex 环境中完成飞书 CLI 登录授权；只给本次工作需要的最小权限。授权状态不确定时，让 Codex 运行只读检查：

   ```bash
   lark-cli auth status --verify
   ```

3. 确认自己已被邀请进 GitHub 仓库，能够查看并审阅 PR。
4. 不要复制其他成员的授权文件、令牌或应用密钥。权限不足时，请项目负责人在飞书或 GitHub 中授权，而不是向别人索要凭证。

## 3. 每个任务的标准操作

### 先在飞书把工作说清楚

1. 在看板新建或找到对应事项。新事项默认「待确认」；确认后无人认领为「待处理」。
2. 至少写四项：要解决什么、影响或复现方式、预期结果、验收标准。可以附截图、页面链接或相关文档。
3. 准备做的人填入自己为负责人，状态改为「处理中」。

### 再让 Codex 协助开发

把飞书事项链接和目标一起发给 Codex：

```text
项目：落笔 AI
飞书事项：<粘贴看板记录或链接>
目标：<要解决的问题或要实现的改善>
范围：只修改 <模块/文件>；不要改动 <明确排除的部分>
验收：<可以观察和验证的结果>
请先读取并给出实施计划；确认后再创建分支和修改代码。
```

第一步先让 Codex 读取和计划，确认范围正确后再明确说「按该方案执行」。遇到报错时，把完整错误信息、发生位置和已尝试的操作发给 Codex。

### 通过 PR 交付代码

1. 让 Codex 从最新 `main` 创建分支，例如 `fix/xxx` 或 `feat/xxx`。
2. 让 Codex 在 PR 中填写关联飞书事项、改动内容、验证方式和风险；PR 链接回写到看板。
3. 邀请至少一位其他协作者审阅。**不得直接推送或合并到 `main`。**
4. 合并后由非开发者优先验收；通过才把飞书事项改为「已完成」，未通过则改回「处理中」并说明现象。

## 4. 最常用的四句话

- “读取这条飞书事项，帮我把问题、可能原因和验收标准整理出来；先不要改任何内容。”
- “按这条事项创建开发方案；只改指定模块，先列出会修改的文件，等我确认再执行。”
- “为已确认的方案创建分支和 PR，按模板写清验证方式；不要直接修改 main。”
- “PR 已合并，请按飞书的验收标准给我一份测试清单，并告诉我如何回写看板状态。”

## 5. 人和 AI 的职责边界

| AI 可以高效完成 | 仍由人确认 |
| --- | --- |
| 读代码、定位线索、起草方案、生成测试清单、创建分支和 PR 草稿、整理飞书记录 | 是否做这项改动、范围与优先级、账号授权、密钥处理、PR 审阅、合并和最终验收 |
| 把讨论转成结构化文档和任务 | 信息是否真实、是否泄露敏感数据、是否符合用户需求 |

AI 的输出不是自动正确。提交前至少核对三件事：改动范围是否正确、测试是否实际运行、飞书事项和 PR 是否互相链接。

## 6. 当天的最小闭环

1. 飞书有一条清楚的事项，并写好验收标准。
2. 只有一位当前负责人，状态正确。
3. 代码通过 PR 进入 `main`，并有其他人审阅。
4. 验收结果回到飞书看板；失败也如实记录并继续跟踪。

群聊用来快速讨论，飞书看板和 GitHub PR 用来留下最终结论。只要每次都完成这个闭环，四个人同时借助 AI 工作也不会失去进度、责任和代码历史。
