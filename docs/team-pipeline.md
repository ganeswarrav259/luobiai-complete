# 落笔 AI 团队协作 Pipeline（飞书 × GitHub）

本规范适用于「落笔 AI」当前四人协作。目标是让每一项问题和改善都有唯一入口、明确负责人、可审阅代码和可验证结果。飞书负责管理工作与验收，GitHub 负责保存代码、审阅与合并记录。

> **一句话原则：** 先在飞书建记录，再认领和开发；代码只通过 PR 进入 `main`；合并后必须回到飞书完成验收记录。

## 1. 协作工具与唯一事实源

| 场景 | 唯一事实源 | 必须记录的内容 |
| --- | --- | --- |
| 问题、需求、优先级、负责人、验收 | [飞书「落笔 AI｜问题与改善看板」](https://acnz5q7jux97.feishu.cn/base/DounbHrlaaOj49s7rG5cPTSsnUg) | 问题描述、状态、负责人、验收标准、PR 链接、验收结果 |
| 代码、分支、评审、合并历史 | GitHub 仓库 | 分支、提交、PR、审阅意见、合并记录 |
| 临时讨论 | 飞书群聊 | 只讨论；结论必须回写到飞书看板或 PR |

## 2. 标准流水线

### 提出：先建立飞书记录

1. 任何人发现 Bug、改善点或需求，先在看板新建一行，状态设为「待确认」。
2. 写清楚：现象或目标、复现步骤或使用场景、影响范围、预期结果；能附截图或链接就附上。
3. 由团队快速确认类型、优先级和验收标准。未认领的已确认事项状态为「待处理」。

### 认领：一个事项只能有一个当前负责人

1. 准备做的人在看板填入自己为负责人，并把状态改为「处理中」。
2. 负责人先确认验收标准；如果范围不清楚，先在飞书记录或 GitHub PR 中提出，不直接凭猜测开发。
3. 较大的技术讨论可补建 GitHub Issue；Issue 链接回写到同一条飞书记录。小改动不强制建 Issue。

### 开发：从 main 拉分支，不直接改 main

- 从最新 `main` 创建短生命周期分支，例如 `fix/login-loading`、`feat/script-editor`、`docs/team-pipeline`。
- 一次 PR 尽量只解决一个看板事项；发现无关问题，另建一条飞书记录。
- 提交信息说明改动意图；涉及界面或行为变化时，保留截图、预览链接或复现说明。

### 提交 PR：把工作交给团队审阅

1. 向 `main` 发起 PR，使用仓库 PR 模板，填写关联飞书记录、改动内容、验证方式与风险/回滚方式。
2. 将 PR URL 回写到飞书看板的「GitHub Issue/PR URL」字段。
3. 指定至少一位其他协作者审阅；PR 作者不能代替审阅者批准自己的改动。

### 审阅与合并：保护 main

- `main` 已启用保护：至少 1 位协作者批准、讨论已解决后才能合并；不直接推送 `main`。
- 审阅者检查：是否符合验收标准、是否影响已有功能、验证是否可信、是否有明显回滚风险。
- 有修改意见时，由负责人继续在原 PR 更新；所有意见解决后再合并。

### 验收与关闭：合并不是终点

1. 合并后由非开发者优先在预览环境或本地按验收标准验证。
2. 通过：看板状态改为「已完成」，在最近更新或备注中写明验收人和日期。
3. 未通过：状态改回「处理中」，保留原 PR 链接并说明失败现象；必要时开新的修复 PR。

## 3. 看板状态与操作映射

| 看板状态 | 代表含义 | 下一步 |
| --- | --- | --- |
| 待确认 | 新提出，尚未统一理解 | 补全信息、确认优先级与验收标准 |
| 待处理 | 已确认，但无人认领 | 任一成员可认领 |
| 处理中 | 已有负责人正在开发或调查 | 维护分支与 PR；遇阻及时说明 |
| 待验收 | PR 已合并，等待独立验证 | 按验收标准测试并记录结果 |
| 已完成 | 已验证达到验收标准 | 关闭；有新问题再建新记录 |

## 4. 角色与节奏

当前不设固定分工，但每个事项必须临时明确三种角色：

- **提出人**：负责把问题说清楚。
- **负责人**：负责推动开发与 PR。
- **验收人**：负责独立验证，尽量不是同一位负责人。

四人轮换即可。

- 每天：负责人在结束当天前更新看板；若被阻塞，写明阻塞原因、需要谁决定或提供什么。
- 每周一次 20 分钟同步：只看「待处理」「处理中」「待验收」三类，处理认领、阻塞、验收和优先级调整。
- 讨论有结论后：由发起人或负责人在当天回写到看板或 PR，群聊不作为最终记录。

## 5. P0 紧急问题

P0 指核心流程无法使用、数据风险或对外演示被阻断。

处理顺序：立即建飞书记录并标为 P0 → 指定负责人 → 建修复分支和 PR → 至少一位协作者快速审阅 → 合并后独立验证 → 当天补齐原因、影响和后续预防措施。

即使紧急，也不直接推送 `main`。

## 6. 完成定义（Definition of Done）

- 飞书记录包含清晰验收标准、负责人和关联 PR 链接。
- PR 已按模板说明改动和验证方式，并至少通过一位协作者审阅。
- PR 已合并到 `main`，且无未解决的关键讨论。
- 验收人在预览环境或本地验证通过，飞书状态更新为「已完成」。
- 若产品行为、部署方式或团队流程发生变化，对应说明已同步更新。

## 7. 禁止事项

- 禁止绕过 PR 直接向 `main` 推送代码。
- 禁止只在群聊说“已修复”而不更新飞书记录。
- 禁止没有验收标准就把事项标为完成。
- 禁止在一个 PR 混入多个无关改动；无关问题另建记录。

本规范从即日起执行。若流程本身造成阻塞，在看板新建一条「改善」记录讨论，并同步更新本文件和飞书说明。
